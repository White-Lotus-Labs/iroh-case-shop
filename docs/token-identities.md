# Token identities and Testnet mocks

The machine-readable registry is `config/tokens.testnet.json`. It records 12 selected mocks, including the three existing tokens, and four exclusions. All mocks are unofficial Iroh Case Shop Testnet collectibles with no monetary value. wNEAR, stNEAR, LiNEAR and rNEAR mocks have no yield, backing, or redemption. Their names do not imply a relationship with the original projects.

The shared `iroh-mock-token` binary initializes exactly 100,000 whole tokens to a separate Testnet inventory account. There is no post-initialization mint method, owner role, or administrative method. The existing private `new({asset, owner_id})` initializer remains unchanged. Initializer asset strings are uppercase, including `MPDAO`, `WNEAR`, `STNEAR`, `LINEAR`, and `RNEAR`. Metadata uses the canonical symbol casing recorded below. Account access keys remain a separate NEAR protocol permission; holding a full-access account key permits code replacement, so the absence of a contract admin method does not make the account immutable.

## Evidence collected on 2026-11-11

Read-only `ft_metadata` requests to [NEAR Mainnet RPC](https://rpc.mainnet.near.org) returned the exact identifiers and decimal precision recorded in the registry. Snapshot block heights were 224058639 through 224058646 for new candidates and 224058985 for the existing three identities. Block hashes are retained per token. RPC metadata alone proves what a contract reports; the primary sources below bind the intended project to that contract. Live token responses do not prove project activity, backing, financial safety, or endorsement.

- BLACKDRAGON uses `blackdragon.tkn.near`, 24 decimals. The community DAO's [official whitepaper](https://blackdragon.meme/whitepaper/) publishes this exact NEP-141 account. The name Black Dragon appears on unrelated chains, so the ticker alone is insufficient.
- NEKO uses `ftv2.nekotoken.near`, 24 decimals. The [original migration announcement](https://gov.near.org/t/announcement-please-upgrade-your-neko-token-to-neko-v2/25179) explicitly replaces the old NEKO token with v2. The current [community site](https://nekoonnear.com/) publishes the same account and describes the original team's handover. Old NEKO contracts and unrelated NEKO tokens must not be substituted.
- mpDAO uses `mpdao-token.near`, 6 decimals. [Meta Pool's contract inventory](https://docs.metapool.app/for-developers/meta-pool-contracts/near-network/) lists this governance token separately from deprecated META. Its on-chain symbol is `mpDAO`.
- GEAR uses `gear.enleap.near`, 18 decimals. The [official Tinker Union app](https://tinkerunion.com/) ships this account in its public [TinkerApp JavaScript bundle](https://tinkerunion.com/assets/TinkerApp-BVafj1kl.js), retrieved during verification. The bundle is a versioned frontend asset and its URL can change. This is NEAR Tinker Union GEAR, not a Gearbox or Gear Network token with the same ticker.
- PURGE uses `purge-558.meme-cooking.near`, 18 decimals. The [official Forgive Me Father site](https://www.absolveme.ai/) embeds this exact NEAR account in its delivered HTML and links its NEAR trading route. Its Solana representation is a different chain identity and is not the selected contract.
- wNEAR uses `wrap.near`, 24 decimals. NEAR's [Wrapped NEAR proposal and closure discussion](https://github.com/near/NEPs/issues/530) identifies the adopted wrapping contract and confirms no transition to the proposed replacement took place. The mock only copies the transferable token identity. It cannot wrap or unwrap native NEAR.
- STNEAR uses `meta-pool.near`, 24 decimals. [Meta Pool's contract inventory](https://docs.metapool.app/for-developers/meta-pool-contracts/near-network/) identifies the stNEAR contract. On-chain metadata reports `STNEAR`, while the project commonly writes stNEAR. The mock has no staking or redemption methods.
- LINEAR uses `linear-protocol.near`, 24 decimals. The [official LiNEAR repository](https://github.com/linear-protocol/LiNEAR) publishes its Mainnet token contract separately from its Aurora bridge representation and Testnet deployment. On-chain metadata reports `LINEAR`. The mock has no staking or redemption methods.
- rNEAR uses `lst.rhealab.near`, 24 decimals. [Rhea Finance's official contract inventory](https://guide.rhea.finance/developers/contracts) identifies its LST contract as the manager of rNear tokens. On-chain metadata reports `rNEAR`. It is distinct from the RHEA governance token and the mock has no staking or redemption methods.

The existing SHITZU, RHEA, and AURORA mocks remain `iroh-test-shitzu.testnet`, `iroh-test-rhea.testnet`, and `iroh-test-aurora.testnet`. They retain their original six decimals and supply of `100000000000` raw units. Their canonical Mainnet identities report 18 decimals, which is recorded separately and must not overwrite the Testnet values. [Rhea's tokenomics](https://guide.rhea.finance/docs/tokenomics) identifies `token.rhealab.near`. [Aurora's own walkthrough](https://doc.aurora.dev/blog/aurora-chains-demo/) identifies `aaaaaa20d9e0e2461697782ef11675f668207961.factory.bridge.near`. SHITZU's canonical metadata at `token.0xshitzu.near` was read to preserve an explicit identity record; its existing selection is grandfathered and this pass did not establish fresh project activity from its primary site.

## Excluded candidates

- META at `meta-token.near` still returns metadata with `$META`, 24 decimals. [Meta Pool's official documentation](https://docs.metapool.app/for-developers/meta-pool-contracts/near-network/) labels it deprecated. Use mpDAO for the active governance identity. A functioning legacy contract does not make META current.
- SWEAT at `token.sweat` returns 18 decimals and remains functional at verification time. The [official sunset notice](https://update.swe.at/) says Sweat Wallet and the current SWEAT services end on December 30, 2026 and a later decision will address the token contract. It is excluded conservatively from this active mock collection. The [official claim-contract source](https://github.com/Sweat-Foundation/sweat-claim) binds the NEAR token identity to `token.sweat`.
- LONK at `token.lonkingnearbackto2024.near` returns 8 decimals. Its advertised [project domain](https://lonk.meme/) redirected to an unrelated blog during this verification. Current primary project identity and activity could not be established. No LONK mock is allocated to cases.
- UWON could not be verified from a current primary project source. The advertised [official site](https://uwon.lol/) could not be retrieved. The candidate account `438e48ed4ce6beecf503d43b9dbd3c30d516e7fd.factory.bridge.near` is retained only as an unverified bridge identity, with no asserted canonical decimals or selected mock. Third-party ticker matches are insufficient to choose between a bridge representation and an asserted native NEAR identity.

No excluded candidate has an intended case, a generated mock key, or an enabled deployment record. An explicit future historical-collectible decision would require a new review.

## Reusable verification and key preparation

Run `python3 scripts/token-preflight.py --validate-only` for an offline registry check. Run with `--canonical` to read current canonical metadata, or without it to read the mock metadata, supply, and inventory balance. `--assets BLACKDRAGON NEKO` limits live reads. The script never signs or sends a blockchain transaction. It rejects duplicate identities, wrong mock accounts, decimal drift, incorrect fixed supply, and missing no-value or derivative disclosures.

`swift -module-cache-path /private/tmp/iroh-swift-module-cache scripts/prepare-mock-keys.swift --list` lists the approved nine token and four case accounts without touching Keychain. Run without arguments to prepare all 13, or pass exact approved account IDs to prepare a subset. The helper reads the registry and case configuration before any Keychain action. It creates a credential only when that account's dedicated service is absent. Existing entries are checked using public attributes and never replaced or read as secret data. New private key material exists only in process memory until saved in macOS Keychain. Output contains only public keys and service/account identifiers. Redirect it to `config/deployment-keys.testnet.json` for the deployment builder.

Public key generation does not create or deploy an account. Registry `proposed` status means deployment and live verification remain outstanding. A deployment may mark an entry `verified-live` only after checking its metadata, supply, and inventory or case balances against final on-chain state.
